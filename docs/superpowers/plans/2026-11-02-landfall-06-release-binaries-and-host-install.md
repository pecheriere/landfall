# landfall plan 06: Release binaries and `host install` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed tag publishes attested `landfall-agent` and `landfall` binaries beside the image (#21), and `landfall host install <user@host> --host <id>` takes a host from nothing to enrolled, from a release it verified itself, over the operator's own SSH (#22).

**Architecture:** The Dockerfile's builder also produces the static binaries, and `release.yml` attests them in one bundle and publishes them through a draft. `landfall-origin` gains a verifier for a named release file, sharing `verify_bundle`'s checks. The CLI drives the system `ssh`: a read-only probe, an unprivileged upload, and one generated script run once under `sudo`, printed first. The agent gets no self-update and the controller no new route.

**Tech Stack:** Rust 1.99 (edition 2024). No new crate except `url` as a direct dependency of `landfall-core` (already in the tree through `reqwest`); `getrandom` joins `landfall-cli` (already a workspace dependency). OpenSSH's `ssh` on the operator's machine. Python 3 standard library for release scripts, as `crate_age.py` is. `cargo-zigbuild`, and upstream's `zig` by checksum, in the Dockerfile. GitHub-owned actions only, so the allow-list doesn't change.

**Spec:** issues #21 and #22; `docs/design/landfall.md` (sections 3, 4, 5.2, 9, 12); `docs/operations.md` ("Requirements", "Running it under systemd", "Enrolling a host", "Running the agent", "Upgrading"); the public repository baseline that design section 3 refers to.

## Rulings made while writing this plan

Each says what it costs if it is wrong. These are the rulings as amended by the review; the next section says what changed.

- **One plan, six PRs, in order.** PR A: build and check binaries, publishing nothing. PR B: publish them. PR C: verify a release file. PR D: `host install`. PR E: `host upgrade` and the guide. PR F, only after the owner's first tag: that release as a permanent fixture. PR C to E can merge before any release exists. *If wrong:* a late discovery about the real bundle (see the first-tag list) means a follow-up PR on merged code, not a redo.
- **Targets:** `landfall-agent` for linux/arm64 and linux/amd64; `landfall` for those and darwin/arm64, as #21 says. No macOS on Intel, no Windows, and no `landfall-server` binary, whose route remains the image. Linux binaries are static musl from the existing Dockerfile builder, with zig, so there is one way to build them; macOS builds natively on a GitHub-hosted arm64 runner. *If wrong:* adding a target is one line in the build matrix and one in the asset table.
- **One builder invocation.** `cargo zigbuild -p landfall-server -p landfall-agent -p landfall-cli`, so the dependency layer is shared and the PR dry run costs little more than today's image build. Features unify across the three, which can make the agent slightly larger; the size budget would show it. *If wrong:* split the agent into its own invocation and pay for a second compile of the dependency tree.
- **The builder is pinned.** `setup-buildx-action` otherwise runs whatever BuildKit image buildx defaults to, and every binary root will run is built inside it. Every workflow sets `driver-opts: image=moby/buildkit:v0.34.1@sha256:99368f3e46177c6405b9740e4461d91cee004128daeecca78d4ceac50ec1da5c` (published 2026-10-20, digest read for this plan) and `cache-binary: false`. Dependabot can't read a workflow's `driver-opts`, so `.github/buildkit/Dockerfile` holds the same reference as a `FROM` line, never built, for Dependabot's `docker` ecosystem, and a test keeps the two equal. zig is upstream's tarball by `ADD --checksum`, one hash for each platform a build runs on, each checked against its minisign signature; it brings its own LLVM, clang and lld, so no package repository can change the compiler, and a stale Alpine pin can't first show on a cache-free tag build. Dependabot can't bump it, and an outage at ziglang.org fails a build with no cache. Left mutable, and accepted: the runner images, the buildx client that comes with them, and `apk add musl-dev` in the Dockerfile, which reaches build scripts only and, being unversioned, can't fail on a rebuild. `rustup target add` is bound by the digest-pinned toolchain's own 1.99.0 channel. *If wrong:* a Dependabot PR that fails its test until the workflows follow, which is the point.
- **Raw executables, not archives.** The attested digest is then the file the target runs, so the hash checked on the host is the attested one, with no unpacking step on a root path. Licences are their own assets. *If wrong:* Homebrew still accepts a raw file; an archive could be added beside it in a later release.
- **Signing is keyless: one attestation with every file as a subject.** `actions/attest-build-provenance` with `subject-path: out/*` gives one Sigstore bundle, attached to the release as `landfall-<version>.sigstore.json`. No key exists to lose. `sigstore-types` 0.15's `matches_sha256` is an `any` over subjects (read for this plan), so `verify_bundle`'s Sigstore step accepts this shape. The bundle is an asset, not fetched from GitHub's attestation API, because that API can answer `bundle: null` with a compressed `bundle_url` (seen on `cli/cli` while writing this plan). *If wrong:* per-file attestations mean one attest step per file, and the verifier is unaffected.
- **The subject's name is checked as well as its digest.** A bundle vouches for every file of the release, so digest alone would accept the amd64 agent asked for as arm64, or the CLI as the agent. The new check wants a subject with both the exact name and the digest, in the signed statement. `subject-path` names a subject by its basename (read in `actions/attest` at the pin), and the real multi-subject bundle in Task 4 shows the same. *If wrong:* it fails closed, and `check-bundle` catches it before anything is public.
- **One verifier.** `landfall-origin` gains `attestation::verify_file_bundle`, on the same internals as `verify_bundle` (same parse rules, same identity match, Rekor v1 with proof and promise). The identity is constants in the CLI: repository `pecheriere/landfall`, id `1441186089`, owner id `1872741`, `.github/workflows/release.yml`. Numeric ids, so a re-created account can't take over. There is deliberately no flag for another identity. *If wrong:* see forks, below.
- **Forks must change three things, and take on the rest.** A fork that wants `host install` changes `crates/cli/src/project.rs` (repository and both ids), `crates/cli/assets/release-signers` (its own key) and `repository` in the root `Cargo.toml`; a test fails if `project.rs` and `repository` disagree. Workflows take the name from `github.repository`, so they need no edit. The fork must also set up what's in "What only the owner can do": an environment, immutable releases, signed tags. It must publish its own fingerprint in `SECURITY.md` and its own commands in the docs. A fork that won't sign tags has to change preflight and the CLI's check as well, which is its choice to make, and the manual steps in the guide remain for anyone building from source. *If wrong:* a fork reads one more file than this says.
- **`host install` also requires the signed tag, not only the attestation.** #22 names the attestation; the design's reason for signed tags applies more here, since the agent is root-equivalent: a stolen GitHub token can run the workflow but can't sign a tag. **This is separate from a deployment's `origin.signed_tags`, which stays optional:** that option is a host's rule about the releases it deploys, read from its own config. This one is what the CLI trusts about landfall's own binaries, and it reads no config. A deployment with `signed_tags = false` isn't affected, and the guide says so in one line, so nobody reads it as a contradiction. *If wrong:* an empty file refuses cleanly (below), and preflight refuses to publish such a CLI, so the failure is early.
- **Signer keys:** `crates/cli/assets/release-signers` holds one or more `ssh-ed25519 <base64>` lines, with no trailing comment, since a key's comment usually carries a name. Blank lines and whole-line `#` comments are skipped, by Rust and Python alike. **Two keys may overlap for rotation:** release N carries both and is signed by the old one, release N+1 is signed by the new one. A CLI that doesn't know the signer refuses, naming the fingerprints it trusts and saying to get a newer CLI. Removing the old key means a new CLI can't verify old tags, which matters for `--tag` downgrades. A compromised key stays trusted in old CLIs for ever, though an attacker also needs a run of the real workflow. **Before the owner supplies a key,** the file holds none: `host install` and `host upgrade` refuse before connecting, even on `--dry-run`, saying this build trusts no release-signing key and why, and `landfall verify` keeps working, as it reads deployments' config. *If wrong:* a planned rotation is a release early or late.
- **Preflight proves the tag before anyone is asked to approve.** On a tag, `release_preflight.py` reads the tag object through the GitHub API, the same bytes the CLI will read, and checks with `ssh-keygen -Y verify` that it is signed by a key in `release-signers`, names this tag, and points at `GITHUB_SHA`. It also checks the tag matches the workspace version. So a lightweight tag, or one signed by another key, fails while it can still cost only a tag number. *If wrong:* a tag number.
- **Publishing verifies first.** After `check-bundle`, which only reads the bundle's shape, `publish` runs `gh attestation verify` on every file against the bundle being shipped, with the repository, signer workflow, tag ref and commit, before the draft exists. That is an independent implementation checking signature and identity. **It does not prove the Rust verifier accepts the bundle**: Tasks 4 and 5 prove that on a real third-party bundle, and PR F on our own. *If wrong:* the run fails before anything is public, and costs a patch number.
- **The workflow can't attest on a dry run, on purpose.** `verify_bundle` requires build trigger `push`. A `workflow_dispatch` run builds, checks and smoke-tests, then skips `publish`; it writes nothing to Rekor. *If wrong:* the first tag's run fails in `publish`, and the fix goes out under the next tag.
- **The first tag should be a release candidate.** Every real tag makes something immutable, so the first should be one nothing depends on: `v0.1.0-rc.1`, say. It is a prerelease, marked as not latest, and the real `v0.1.0` follows once the first-tag list is clear. *If wrong:* one version number spent.
- **A publish run has one attempt.** The design's rule 4 refuses a release whose image was attested by two attempts, and tags can't be moved. So `publish` fails at once if `GITHUB_RUN_ATTEMPT` isn't 1, and `verify_release_file` also refuses a run URL not ending `/attempts/1`. The way out of any failed release is a new tag, after a version-bump PR, since preflight wants the two equal. A flake anywhere in the run costs that too, as a re-run of any job is attempt 2. Files go up as a draft before the image is pushed, as the draft is the part that can be abandoned. If the final step fails after the image is attested, hosts can deploy that image while the binaries never appear; the design makes the Release object optional, so this is accepted. *If wrong:* a transient failure costs one patch number and one small PR.
- **`release` environment:** `publish` runs in it. GitHub silently creates a missing environment with no protection, so an `environment-guard` job reads it through the API with `check_environment.py`, and `publish` needs that job. It refuses a missing environment, no `required_reviewers` rule, an empty reviewer list, `prevent_self_review` on (nobody could approve) and a null `deployment_branch_policy`. Today's repository has no environments, so the guard fails until the owner acts, and today's `publish` runs without one, which this plan fixes. *If wrong:* if the job's token can't read the environment, the dispatch run shows it before any tag.
- **SSH is the system's `ssh`, never a library.** So the user's agent, `ProxyJump`, tailnet SSH and hardware keys all work and no key material comes near landfall. The forced options, and exactly what was shown for each, are in the table under Global Constraints. An unknown host is refused, and the message says to connect once by hand and compare the fingerprint; landfall never runs `ssh-keyscan` or accepts a key. *If wrong:* password SSH logins are refused outright, which suits the agent-only rule and is stated in the guide.
- **One connection:** a master started first, with `ssh -fNM` and its stderr to a file rather than a pipe (a pipe stays open for the master's life), with its socket in a fresh 0700 directory under `/tmp` (a macOS `$TMPDIR` is too long for a socket), `ControlPersist=60`, closed on exit, so a hardware key is touched once. A slow `y/N` can let it expire, which costs one more touch. *If wrong:* more touches, nothing worse.
- **sudo:** the whole privileged part is one script and one `sudo sh -c '<script>'`, printed first, in full, with its SHA-256. It is passed as an argument so that no file in a user-writable directory is run as root. It holds no secret, and it is final when printed: the upload directory's name is drawn beforehand. With a terminal it uses `-o RequestTTY=force` and sudo's own prompt, so landfall never sees the password; without one it runs `sudo -n true` **before any upload**, then `sudo -n`, and refuses cleanly. Already root runs `sh -c` without sudo. No `sudo -S`, no `doas`. A login shell that doesn't return a quoting check intact (fish, csh) is refused, as what ran could differ from what was hashed. What the target prints during that step goes straight to the terminal, because sudo's prompt needs it: a residual, stated in the guide. *If wrong:* a sudoers file that allows only named commands can't use this; the guide gives the manual steps it already has. On a terminal it asks `y/N` after printing; `--yes` skips that, and no terminal without `--yes` refuses.
- **The upload directory:** the CLI draws 16 random bytes from the OS and names `/tmp/landfall-install.<hex>`. The upload's `mkdir -m 700` fails if anything is there, so nothing can be planted. Because the name is known before the plan is printed, `--dry-run` creates nothing and the printed hash is the hash that runs.
- **Secrets:** the enrolment code goes from `--code-file` over `ssh` stdin into that directory (umask 077), last and immediately before the script. The script reads it through `runuser -u "$SUDO_USER" -- cat`, so a link there gains nothing, into `/var/lib/landfall-agent/.enrol-code`, 0600, owned by the agent, and removes it on every exit path it can catch. It never appears in argv, the printed plan or an error. If the script fails or never starts, the CLI removes the upload directory through a plain `Remote::run` after `run_privileged` returns anything but 0. **The residual** is a connection cut after the upload, or a `SIGKILL`: then the code stays in a 0700 directory of the login user, or in `.enrol-code`, one-time and expiring within the hour. The next run removes it: preflight deletes `.enrol-code`, and the root script removes `landfall-install.*` older than an hour. `GITHUB_TOKEN` is never sent to the target; the unit has `EnvironmentFile=-/etc/landfall/agent.env`, for the operator to fill. *If wrong:* a code exposed on the host for its short life, to the same user who holds sudo.
- **Hash checks are root's.** The script writes the upload to a root-owned `/usr/local/bin/.landfall-agent.new`, mode 0700, through the same `cat`; compares its SHA-256 with the verified digest written in the script; only then sets 0755 and renames. *If wrong:* the login user can already wrap `sudo` through `.bashrc`, so this closes a race, not a whole class.
- **Idempotence and interruption:** every step looks first and changes only what differs, each file arrives by rename, and `agent.key` is only ever touched by `landfall-agent enrol`, which never overwrites it. The script uses `trap cleanup EXIT` and `trap 'exit 129' HUP INT TERM PIPE`, so that a signal stops it instead of returning to the next step with its files gone. A rerun converges, proved for stopping between steps and for signals during one. *If wrong:* a step that isn't convergent; the two tests that kill it exist to find that.
- **The host still decides.** The CLI never talks to the controller, and the code is minted by the operator on the controller as today. An existing `/etc/landfall/fleet.toml` or unit that differs is **refused**, with a diff, unless `--replace-config` or `--replace-unit` is given, because silently replacing the host's own rules would be the one way this command could loosen them. A replaced file is kept as `<file>.previous`. Config comes from the operator's file, checked by `parse_config` before connecting, and must have a deployment for `--host` (else the agent can't start). `install` refuses a different agent binary already there (use `upgrade`). Compose directories must already exist; they are never created. *If wrong:* a little friction on a re-install, by design.
- **A replacement takes effect, or says it hasn't.** The agent reads its config once, so `--replace-config` with no restart would report success with the old rules in force. So a change of config, unit or group writes `/etc/landfall/.restart-pending` before it happens, and the `start` step restarts a running unit if that marker exists, then removes it. The marker means an interrupted run still restarts on the rerun. A stop waits for a deploy in flight, so if the unit is still stopping after the wait, the command says plainly that the old rules stay in force until that deploy ends. *If wrong:* a restart too many, which the agent is built to survive.
- **Knowing an agent is healthy:** the unit has `Restart=always`, so a broken agent never reads `failed`, it cycles. Both `install` and `upgrade` use one shell function: record `InvocationID` first; success is a new `InvocationID`, `ActiveState=active`, and the same id and `NRestarts` after 10 s. Still `activating` or `auto-restart` after 120 s is failure, with the last 20 journal lines. `deactivating` after 120 s isn't failure: a deploy is finishing, and the command says so. *If wrong:* an agent that crashes after more than 10 s is reported healthy; its journal and the controller's host view still show it.
- **Version floors:** Linux 5.8 (documented), systemd 235 (for `NRestarts`), `docker compose` plugin v2, Docker client 20.10, the oldest a compose v2 plugin supports. Checked from client commands, so no sudo is needed to see them; the daemon is checked as the agent's user in the script. Low on purpose: nothing in the repo shows a higher floor is needed. *If wrong:* an old Docker passes this check and the deploy's own preflight refuses it with its own message.
- **Which release:** the CLI's own version, `v<CARGO_PKG_VERSION>`, or `--tag`. Today's workspace version is `0.0.0`, so a release must bump it: preflight refuses a tag that isn't `v<workspace version>`, and a CLI at `0.0.0` refuses to guess and asks for `--tag`. *If wrong:* the tag fails at preflight, which costs a tag number.
- **`host upgrade`:** same verification and script path; touches only the binary and a restart. Refuses a downgrade without `--allow-downgrade`, a host with no unit, and the same version with different bytes (it could be a hand-built or tampered binary, so the flag is needed, and the hash is shown). Keeps `/usr/local/bin/landfall-agent.previous`, by rename, and prints how to go back; it doesn't roll back by itself. It restarts with `--no-block`, as a stop waits for a running deploy (up to three hours). Operator-run, in line with "landfall never deploys landfall". *If wrong:* the new binary fails to start; deployed services are untouched and the printed command restores it.
- **Homebrew tap: a second repository, created by the owner, filled by hand.** `brew install <owner>/landfall/landfall` needs one named `homebrew-landfall`. `release.yml` generates `landfall.rb`, pinned by SHA-256 and attested as a subject, and attaches it. **Nothing commits it automatically:** a workflow that did would take the latest release on `gh attestation verify` alone, which skips the signed tag this plan relies on, so a stolen owner token could reach every `brew upgrade` by the next day. The owner copies one verified file per release, by the recipe in `packaging/homebrew-tap/README.md`, which checks the tag's signature too. Everything else works without a tap. No `curl | sh` script. *If wrong:* a small manual step per release; an automated one later needs its own copy of the key.
- **macOS binaries aren't notarised:** that needs a paid identity and a long-lived certificate, which this project refuses. Homebrew and `gh release download` don't set the quarantine flag; a browser does, and the guide says so. *If wrong:* some people meet a Gatekeeper dialog.

## Global Constraints

- `rust-toolchain.toml` 1.99; workspace lints apply. No `#[allow]`/`#[expect]` without `reason = "..."`. `unsafe_code` forbidden. No `unwrap`/`expect` outside tests. Public error enums are `#[non_exhaustive]`.
- Source files stay under about 800 lines of code, and tests go in their own files, as `foo/tests.rs` and `foo/tests/<scenario>.rs`, naming what they import.
- Public baseline: actions pinned to the full SHA of a release at least 7 days old, with the tag in a comment; `persist-credentials: false`; `--locked`; `timeout-minutes` on test jobs; publish jobs in the `release` environment with no build cache; values through `env`, never inline; `GH_TOKEN=$(gh auth token) uvx zizmor .` reports nothing before a workflow change is pushed.
- Everything fetched, and everything a target prints, is hostile: bodies capped before parsing, text quoted and truncated in errors, no panics. The one exception is the privileged step's inherited stdio, stated as a residual.
- Nothing personal in code, docs, tests or commits: example names only (`app/prod`, `home-1`, `user@host.example`, `https://controller.example`). The project's own repository name and public ids are already public; in code they appear in `crates/cli/src/project.rs` and the root `Cargo.toml`, and in docs where a command needs them. Workflows use `github.repository`.
- **No real host, network or firewall change as part of testing.** Host tests run against a throwaway container with `sshd`: no host mounts, no `--network host`, port published on `127.0.0.1` only.
- Never tag or release, and never `gh release` from a shell: only `release.yml` does that, after the owner's tag and approval.
- Security review (`security-review` skill) before merging PR B, C, D and E, recorded in the PR. Each PR says what was and wasn't verified, separating CI from local.
- Gate before each commit: `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`, `cargo test --workspace --all-features --locked`, `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --locked`, `cargo deny --all-features --locked check`. Iterate with `cargo nextest run -p <crate>`. Python: `ruff check`, `ruff format --check`, `python3 -I -m unittest discover -s .github/scripts -p 'test_*.py'`. Conventional commits, no attribution trailers.

## Review Focus

1. **A valid file of the same release under the wrong name,** such as the amd64 agent as arm64, or the CLI as the agent, must be refused, though its digest is attested → Task 4 `another_files_digest_is_refused_under_this_name`.

3. **An install cut off at any point,** including before the script starts and by a signal during a step, leaves no code behind by the next run, keeps the key and converges → Task 8 `docker_interrupted_at_every_step_converges`, `docker_killed_during_a_step_cleans_up`, `docker_nothing_secret_is_left_behind`.
4. **A host with something already there:** an existing key, a config or unit the operator changed, an agent already running, or rules replaced while it runs → Task 8 `docker_existing_key_survives_a_new_code`, `docker_changed_config_is_refused`, `docker_replaced_config_restarts_the_agent`, and Task 6 `a_code_for_a_running_agent_is_refused_in_the_script`.
